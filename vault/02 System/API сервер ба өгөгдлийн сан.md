# API сервер ба өгөгдлийн сан

> Компанийн дотоод "Open Tee систем" vault-ын дөрвөн тэмдэглэлийг дипломд зориулж нэгтгэсэн, сервер хаяг, нууц, дугаар, хувь хүний мэдээллийг хассан хувилбар. Эх тэмдэглэлүүд K-ийн компьютер дээр үлдэнэ ([[Эх сурвалжийн зураглал]]).

## Тойм
- Open Teever-ийн бүх өгөгдөл нэг REST API-аар дамжина: жолоочийн апп, админ вэб, нийтийн ачаа хянах хуудас, түлшний хяналт (Fuel Tank Warner) бүгд үүнтэй ярьдаг ([[Системийн тойм]]).
- Хаяг: `https://api.opendevelopment.mn/api/v1`. Node.js, Express. Админ вэбтэй Socket.IO-оор шууд (live) холбогдоно.
- Байршуулалт: компанийн өөрийн виртуал сервер (Tokyo бүс) дээр Docker compose-оор API ба Caddy (HTTPS) гэсэн хоёр контейнер. Нэг сервер дээр API, Caddy, түлшний хяналт гурав л ажилладаг.
- Repo: `opendev_server`. 2026-10-19-өөс `main` салбар = live код. Deploy гараар хийгддэг (доор).

## Өгөгдлийн сан
- Supabase Postgres (Tokyo, Pro багц). API нь өгөгдлийн сангийн эзэн хэрэглэгчээр session pooler-ээр холбогдоно.
- Бүх хүснэгтэд RLS асаалттай боловч policy байхгүй. Энэ нь санаатай: өгөгдөлд зөвхөн API хандана, клиент аппууд Supabase-тэй шууд холбогддоггүй. 2026-11-02-ны шалгалтаар 54 хүснэгт бүгд RLS-тэй.
- Файлууд (бичиг баримт, зураг, баримтын PDF): хаалттай (private) bucket, 1 цагийн хугацаатай signed link.
- Migration: дугаартай SQL файлууд `db/migrations`-д. Эзэмшигч Supabase SQL editor-т гараар ажиллуулна. Дүрэм: шинэ скриптэд temp table хэрэглэхгүй, нэг statement-тэй CTE бичнэ.

## Deploy ба rollback
### Ажиллагааны дүрэм
- Live-д нөлөөлөх алхам бүр (deploy, өгөгдлийн санд бичих, DNS, store-д нийтлэх) эзэмшигч тухайн алхам дээр тодорхой "yes" гэж бичсэний дараа л хийгдэнэ.
- Deploy бүр сүүлийн суурь хувилбараас эхэлж, хүлээгдэж буй бүх өөрчлөлтийг агуулна (хуучин салбараас deploy хийхгүй). Түлшний холбоосыг устгах нэг хуучин commit-ийг хэзээ ч deploy хийхгүй гэсэн тусгай дүрэмтэй.
- Хувилбар бүрийн өмнө одоогийн тохиргооны нөөц хуулбар үлдээнэ; rollback гэдэг нь тэр нөөцийг сэргээж контейнерийг дахин асаах явдал.

### Арга (бүрэлдэхүүн тус бүрээр)
| Хэсэг | Deploy | Rollback |
|---|---|---|
| API сервер | Хөгжүүлэгчийн PC дээр `git archive` → серверт хуулах → `docker build` → compose-ийн override файлд image tag солих → `docker compose up -d --no-build api` | Өмнөх compose override-ийн нөөцийг сэргээж `up` |
| Админ вэб | `main` руу merge → Vercel өөрөө build хийж гаргана | Тухайн merge commit-ийг revert хийнэ, Vercel дахин гаргана |
| Fuel Tank Warner | `git archive` → серверт хуулж задлах → `docker compose build` + `up`; `.env` ба override хэвээр | Өмнөх image-ийн tag-ийг `latest` болгож, өмнөх кодын архивыг буцааж задлаад `up` |
| Landing | PC-ээс `vercel deploy --prod` | Vercel дээр өмнөх deployment-ийг promote |
| SQL | Дугаартай файлыг эзэмшигч SQL editor-т ажиллуулна | Migration бүрт undo скрипт (жишээ: дугуйны импорт) |

- Техникийн тэмдэглэл: PC-ээс SSH зөвхөн Windows OpenSSH-ээр; кирилл агуулсан PowerShell скрипт UTF-8 BOM-той байх ёстой; хуучин түр хавтсыг устгаагүй бол clone чимээгүй бүтэлгүйтнэ.
- 2026-10-26: хоёр дахь компьютерээс (зөөврийн) серверт хандах тохиргоо: тусдаа SSH түлхүүр, `authorized_keys`-д нэмэх нь live алхам, нууц түлхүүр компьютерээс гарахгүй, зөвхөн `.pub` мөр солилцоно, буцаах скрипттэй.

## Аюулгүй байдал
### Өмнөх гүйцэтгэгчээс хүлээн авалт
- Анхны кодыг гадны компани хийсэн; зорилго нь хамтын ажиллагааг аль болох хурдан, цэвэрхэн дуусгах. Хүлээлцэх баримт бэлтгэгдсэн (хуульчийн шалгалт, илгээх алхам хүлээгдэж байна).
- Шилжүүлэх ёстой данс, эрхүүд: App Store / Google Play-ийн худалдагч данс, Firebase төсөл, ДАН-ы client бүртгэл. Гүйцэтгэгчийн Vercel integration админ repo-г уншиж чадсаар байсан тул салгах нь эзэмшигчийн алхам.
- Хуучин MongoDB/Atlas гүйцэтгэгчийн данс дээр үлдсэн.

### Нууц түлхүүр
- Серверийн repo-ийн түүхэнд хуучин `.env`, SSH түлхүүр, Firebase/Apple түлхүүр, 3.4 GB хуучин upload файл үлдсэн. Шийдвэр: түүхийг одоохондоо дахин бичихгүй, харин серверийн repo-г гадны хүнд нээхгүй.
- Түлхүүр солих жагсаалтыг серверийн repo-ийн аюулгүй байдлын баримтад хөтөлдөг; гадны үйлчилгээний түлхүүрийг дур мэдэн сольдоггүй; vault-д нууц үг, түлхүүр хэзээ ч бичдэггүй.
- Өгөгдлийн сангийн нууц үг солих, JWT secret солих нь эзэмшигчийн гараар хийх алхам (кодоор засагдахгүй).

### Сургамж (дипломд)
1. Гадны гүйцэтгэгчээс код хүлээн авахдаа данс, түлхүүр, repo түүх гурвыг тусад нь шалгах.

3. Эрхийн шалгалтыг token-д итгэхгүй, өгөгдлийн сантай тулгах.
